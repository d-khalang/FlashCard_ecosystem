# Bot architecture refactor

Goal: make the bot core reusable so the Telegram bot and the Mini App become thin
clients of one set of use cases. Work happens on `main` first; the Mini App is then
rebuilt on top of it. Every step is behavior-preserving unless stated.

## Problems (root causes)

| # | Problem | Mini App symptom it caused | Status |
|---|---------|----------------------------|--------|
| 1 | Language is read from global settings everywhere instead of injected config (one instance per language is intended) | Per-language databases, authority DB, language exchange, two builds | Done (i18n singleton left for #7) |
| 2 | No use-case layer: business logic lives in Telegram handlers; scheduler copies `/get` | Parallel core, `enrolled()` branches patched into handlers | Done |
| 3 | Services don't own their data: raw `cols` everywhere, several services write `users` | CAS checks, fencing, revisions | Done |
| 4 | A review is not an entity: only scattered flags (`has_pending`, `pending_message_id`) tied to a Telegram message | Attempts, receipts, dispatch tokens, presence | Code done; rollout pending (production steps 2–6) |
| 5 | Cards are regenerated by the LLM on every review; only the latest should be stored (fallback when all providers fail) | Preparation store, content versions, saved fallback, job queues | Done |
| 6 | Quota is ad hoc: counters on the user doc, limits frozen at import, trial derived from `created_at` | Parallel quota/allowance system, `miniapp_accounting` fencing | Done (own-key LLM calls deferred) |
| 7 | Global singletons (`settings`, `i18n`) imported at module level | Runtime-mode explosion, separate runners | Open |
| 8 | Writes are not idempotent (regex de-duplication, no unique index) | `action_id` required on every call | Code done for card saves; rollout pending (step 3) |
| 9 | Loose types: `user_id` is `str` or `int`, dicts instead of models, ISO strings compared as text | BSON Int64 session bug | Open |
| 10 | No shared composition root: dispatcher data dict; startup wiring duplicated in `bot.py` | `MiniappRuntime` built its own composition | Done |

## Production rollout (one update after the full refactor)

Nothing from this refactor is deployed yet. Everything ships in **one update** once the
refactor is finished, then these production steps run in order:

1. Back up each language database. In `kartino-deploy`, set `LANGUAGE_VALIDATOR` in each
   instance's env (`italian` for IT, `latin` for EN); without it the new image does not start.
2. Deploy with `REVIEW_PAUSE_RULE=legacy` (default). New writes (`current_review`,
   `last_seen_at`) start alongside the legacy fields; behavior is unchanged.
3. Backfill each language DB (dry run, check counts, then `--apply`):
   - `python -m flashcard.migrations.backfill_current_review`
   - `python -m flashcard.migrations.backfill_created_at`: missing trial starts become
     the user's oldest expression (or the run time without expressions). Users counted
     in `trial_ends_now` lose their permanent trial at once; that is intended.
   - `python -m flashcard.migrations.dedupe_expressions` (after `backfill_current_review`):
     removes duplicate cards and builds the unique `(user_id, value)` index. Deletes data,
     so only after the step-1 backup. A new, empty database also needs this run once
     (`--apply` builds the index); nothing else creates it.
4. Observe the `Review-state shadow compare` log line for a few days:
   `missing_current_review` ≈ 0, no unexplained `new_pauses`.
5. Switch: set `REVIEW_PAUSE_RULE=current_review` and restart (no new image).
   Rollback: set it back to `legacy` and restart.
6. After the switch is validated: the **contract** step is a **separate, later update**
   (it deletes the rollback path), see "Remove after the migration is validated".
7. Also in a later update: remove the legacy settings-menu `"toggle"` callback
   (`SettingsUseCases.toggle_review_mode` and its branch in `handle_settings_select`).
   Menus sent before the deploy still carry it; after removal, pressing the review-mode
   button on such an old menu shows the "invalid value" alert (`set_review_mode`
   rejects `"toggle"`), and `/settings` gives a working menu. Wait a few weeks after the deploy.

## #3/#4 Review state: progress

`has_pending` mixed two meanings: "a review is unanswered" and "the user showed up,
so resume". It is replaced by two facts on the user document:

- **`users.current_review`** (`expression_id`, `direction`, `message_id`, `sent_at`),
  written only by `ReviewStateStore`: the delivered card still waiting for a grade.
  A newer card replaces it; grading or removing that card clears it.
- **`users.last_seen_at`**: any message or callback (`UserService.record_seen`).

Scheduler rule after the switch: due if no current review, **or** seen after it was
sent, plus the existing interval. Candidate selection keeps the 12 h cooldown; an
ungraded card is not excluded beyond it.

### Data-model rules

- Data that must change together lives in one document (Mongo is atomic per document).
- One writer per field group, `$set`/`$unset` on its own paths; never replace a whole doc.
- Cross-document flows run in a use case in a fixed order; a failed second write must
  self-heal (e.g. grade: expression stats first, then user review state).
- Keep only the latest: no history collections until a feature needs them.

Planned field groups:

| Document | Field group | Only writer |
|---|---|---|
| expression | identity (`value`, `created_at`, `status`) | `ExpressionStore` |
| expression | stats + `review_rev` | grading |
| expression | `last_card` (card + settings it was made with, #5) | `ExpressionService.update_expression_sent` |
| user | profile, settings, onboarding, `last_seen_at` | `UserService` |
| user | `consumption` | `ConsumptionService` |
| user | `current_review`, `last_graded` (one-level undo snapshot), `last_reviewed_at`, legacy `has_pending` | `ReviewStateStore` |

Decisions: one-level undo only (deeper undo corrupts grading); undo restores the
snapshot only if `review_rev` still matches. Reviews generate fresh content; the stored
card is a fallback when every provider call fails (not counted against quota).
A separate `review_attempts` collection was tried and dropped: nothing needed history,
and it split the scheduler's "due" query across two collections.

### Ownership fixes

- [x] **One creator of user documents.** `UserService.record_seen` (trace middleware,
  now awaited before the handler) is the only upsert on `users`; every other writer
  updates existing users only. Before, a user's first update could reach a handler
  that upserted without `created_at` (save, settings, pause), and `$setOnInsert` never
  filled it later: such users keep the trial (plus) limits forever.
  Existing users missing `created_at`: `flashcard.migrations.backfill_created_at`
  (rollout step 3). Dead `ExpressionService.update_user_last_push` removed.
  Guarded by `tests/unit/test_user_creation_contract.py`: only `record_seen` may
  upsert `users`, and the Telegram dispatcher must run `TraceMiddleware`.
  **Mini App:** its auth/launch step must call `record_seen` too; add its test there.
- [x] **`ExpressionService` no longer writes `users`.** Review state moved to
  `ReviewStateStore`: `mark_pending` (send), `clear_pending` (save, import, remove),
  `record_reviewed` (grade: `last_reviewed_at` + clear `has_pending`, one update).
  `last_push_at` is no longer written (never read). Guarded by
  `tests/unit/test_data_ownership.py`: only `UserService`, `ConsumptionService` and
  `ReviewStateStore` write `users`. `TRIAL_DAYS` replaces the literal 14.
- [x] **Typed settings setters.** `UserService.update_setting(field, value)` wrote any
  field. Replaced by `set_target_level`, `set_review_interval`, `set_primary_language`,
  `set_secondary_language`, `set_review_mode`; each enforces its rules (now in
  `schemas/user.py`, next to the fields). `SettingsUseCases` only parses input.
- [x] **Idempotent toggles.** Pause/Resume and the review-mode button were read-then-write
  flips: a double tap or a stale button flipped the setting back. The buttons already
  name what the user wants, so they now call `set_active(active)` and
  `set_review_mode(mode)` (single `$set`, atomic). The review-mode button's callback
  names the other mode. `toggle_active_status` and the unused `get_user_status` removed.
- [x] **Each service gets only its own collection.** Services took the whole `cols`
  dict, so any service could reach any collection. Now `ExpressionService(expressions)`,
  `UserService(users)`, `ConsumptionService(users)`, `ReviewStateStore(users)`,
  `VerbService(conjugations)`. `build_core` in `composition.py` is the only place that
  hands collections out (both startup paths use it); `cols` is no longer injected into
  handlers. Guarded by `tests/unit/test_data_ownership.py` (only the composition root,
  `db/mongo.py` and the migrations index `cols`; no `self.cols`; `build_core` wiring).
- [x] **No reads of `users` outside its owners.** `ExpressionService.get_review_candidate`
  takes `review_mode` from the use case (which loads the user first; same number of
  reads, one fewer for the scheduler). The scheduler's queries moved into
  `UserService.active_users_reviewed_before` / `active_users_possibly_paused`, which
  read each document safely and report unreadable ones. Guarded by
  `test_only_owners_read_users`.

- [x] **Per-user isolation in the scheduler.** One unreadable user document (schema
  error, bad date) no longer stops a tick: `find_users_due_for_review` skips it, logs
  it and reports it to the admin with the send failures (`Unreadable user document`).
  The shadow compare counts such users as `unreadable`. A bad document is reported
  every tick until fixed.

## #1 Language as instance config: plan

Decision (2026-10-19): one fully independent instance per language (own bot, database,
Mini App, config). The project is open source and adaptable per language; nothing is
shared across languages (no shared quota, trial or language switch). Rejected: merging
the databases, and one shared `users` collection keyed by `(user_id, language)`.
Mini App consequence: its authority DB, language exchange and second build go away.

- [x] `LanguageConfig` (`flashcard/language.py`: code, name, flag, UI locale, validator,
  conjugation, user defaults) built once per startup path and passed through
  `build_bot_dispatcher`, `build_core`, handler data (`language`) and `scheduler_loop`.
  `UserService` (`defaults` required) fills missing user settings from it (stored values
  win); `UserDB` has no defaults for them, so the config is their only source.
  `ReviewUseCases` gets the same defaults; the `schemas/defaults.py` constants are gone.
  Guard: `tests/unit/test_language_config.py`. Exception: the `i18n` singleton still reads
  `UI_LOCALE` / `LEARNING_LANGUAGE_NAME` (#7).
  Custom validators now receive the `LanguageConfig`, not `Settings`. `VerbService` lost
  its `ENABLE_CONJUGATION` check: it is only built when conjugation is on.
- [x] Validator chosen explicitly in config; the `auto` guess is gone (non-Italian →
  `latin` silently rejected non-Latin scripts). `LANGUAGE_VALIDATOR` is required: a
  missing, `auto` or unknown value fails at startup (`get_language_validator`) and
  lists the choices. Settings still load without it, so imports and tests don't need it.
- [x] #8: unique index `user_value_unique_ci` on `(user_id, value)` with a case-insensitive,
  accent-sensitive collation (`en`, strength 2): "Ciao" = "ciao", "perché" ≠ "perche",
  `tavolo/a` unchanged. No new field: `value` keeps its case for display (German nouns,
  names). Saves catch the duplicate-key error, so a double tap or retry cannot create a
  second card; `/import` inserts unordered and drops repeats within its input.
  Migration `dedupe_expressions` (rollout step 3): MongoDB groups the cards with the index's
  own collation (`$group`), because no Python fold matches it (MongoDB 7: "ß" ≠ "ss", NFC =
  NFD "é", "ﬁ" = "fi"). Keeps the card with most reviews (forward + reverse; ties keep the
  oldest, legacy datetime `created_at` included), treats each removed card like a `/remove`
  (clears `current_review` if it pointed there; clears the legacy pause only if the user is
  paused, a removed card held the pending message and no remaining card does), then builds
  the index. Non-string `user_id` / `value` are reported, not touched. Values differing only
  by surrounding spaces stay distinct for both the index and the migration (input is trimmed
  on save). Verified on a disposable MongoDB 7.

Out of scope: per-user interface locale (new feature, own item later).

## #6 Quota as its own concept: progress

Decisions (2026-10-28): over quota, a stored card is still sent (free); only results the
user receives are counted; the trial stays derived from `created_at` (no migration).

- [x] `QuotaPolicy` (`app/quota.py`) owns tier limits, the trial (`TRIAL_DAYS`) and
  own-key handling. It is a rule, not a data owner, so it lives in `app/`, not `services/`. `check(user, kind) -> Allowed | QuotaExceeded(tier, limit)`;
  `record(user_id, kind, allowed)` counts in the bucket `check` chose.
  `ConsumptionService` only stores the counters.
- [x] Limits are read from the injected settings on every check (no `TIER_LIMITS` frozen

- [x] Creation, review, story and `/import` use it; the use cases take `quota`

  they have no limit).
- [x] Behavior change: over quota, `prepare_next` returns the stored card (label "Saved
  version") instead of `QuotaExceeded`; `QuotaExceeded` only when none is stored.
- [x] Behavior change: `/import` counts one card generation only when it saves something;
  parse failures, nothing found, invalid language and all-duplicates are free.
- [x] Tests: `tests/unit/app/test_quota.py` (ported from `test_user_quota.py`, plus the
