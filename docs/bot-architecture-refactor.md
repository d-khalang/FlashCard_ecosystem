# Bot architecture refactor

Goal: make the bot core reusable so the Telegram bot and the Mini App become thin
clients of one set of use cases. Work happens on `main` first; the Mini App is then
rebuilt on top of it. Every step is behavior-preserving unless stated.

## Problems (root causes)

| # | Problem | Mini App symptom it caused | Status |
|---|---------|----------------------------|--------|
| 1 | Language is a deployment (one process + database per language), not data | Per-language databases, authority DB, language exchange, two builds | Open |
| 2 | No use-case layer: business logic lives in Telegram handlers; scheduler copies `/get` | Parallel core, `enrolled()` branches patched into handlers | In progress |
| 3 | Services don't own their data: raw `cols` everywhere, several services write `users` | CAS checks, fencing, revisions | Open |
| 4 | A review is not an entity: only scattered flags (`has_pending`, `pending_message_id`) tied to a Telegram message | Attempts, receipts, dispatch tokens, presence | In progress |
| 5 | Cards are regenerated by the LLM on every review, never stored | Preparation store, content versions, saved fallback, job queues | Open |
| 6 | Quota is ad hoc: counters on the user doc, limits frozen at import, trial derived from `created_at` | Parallel quota/allowance system, `miniapp_accounting` fencing | Open |
| 7 | Global singletons (`settings`, `i18n`, `TIER_LIMITS`) imported at module level | Runtime-mode explosion, separate runners | Open |
| 8 | Writes are not idempotent (regex de-duplication, no unique index) | `action_id` required on every call | Open |
| 9 | Loose types: `user_id` is `str` or `int`, dicts instead of models, ISO strings compared as text | BSON Int64 session bug | Open |
| 10 | No shared composition root: dispatcher data dict; startup wiring duplicated in `bot.py` | `MiniappRuntime` built its own composition | Open |

## Production rollout (one update after the full refactor)

Nothing from this refactor is deployed yet. Everything ships in **one update** once the
refactor is finished, then these production steps run in order:

1. Back up each language database.
2. Deploy with `REVIEW_PAUSE_RULE=legacy` (default). New writes (`current_review`,
   `last_seen_at`) start alongside the legacy fields; behavior is unchanged.
3. Backfill each language DB (dry run, check counts, then `--apply`):
   - `python -m flashcard.migrations.backfill_current_review`
   - `python -m flashcard.migrations.backfill_created_at`: missing trial starts become
     the user's oldest expression (or the run time without expressions). Users counted
     in `trial_ends_now` lose their permanent trial at once; that is intended.
4. Observe the `Review-state shadow compare` log line for a few days:
   `missing_current_review` ≈ 0, no unexplained `new_pauses`.
5. Switch: set `REVIEW_PAUSE_RULE=current_review` and restart (no new image).
   Rollback: set it back to `legacy` and restart.
6. After the switch is validated: the **contract** step is a **separate, later update**
   (it deletes the rollback path), see "Remove after the migration is validated".

## #3/#4 Review state: progress

`has_pending` mixed two meanings: "a review is unanswered" and "the user showed up,
so resume". It is replaced by two facts on the user document:

- **`users.current_review`** (`expression_id`, `direction`, `message_id`, `sent_at`),
  written only by `ReviewStateStore`: the delivered card still waiting for a grade.
  A newer card replaces it; grading or removing that card clears it.
- **`users.last_seen_at`**: any message or callback (`UserService.record_seen`).

Scheduler rule after the switch: due if no current review, **or** seen after it was
sent, plus the existing interval. Candidate selection keeps the 12 h cooldown; an
ungraded card is not excluded beyond it.

### Data-model rules

- Data that must change together lives in one document (Mongo is atomic per document).
- One writer per field group, `$set`/`$unset` on its own paths; never replace a whole doc.
- Cross-document flows run in a use case in a fixed order; a failed second write must
  self-heal (e.g. grade: expression stats first, then user review state).
- Keep only the latest: no history collections until a feature needs them.

Planned field groups:

| Document | Field group | Only writer |
|---|---|---|
| expression | identity (`value`, `created_at`, `status`) | `ExpressionStore` |
| expression | stats + `review_rev` | grading |
| expression | `content` (prefs it was made for + sections) | `CardContentStore` |
| user | profile, settings, onboarding, `last_seen_at` | `UserService` |
| user | `consumption` | `ConsumptionService` |
| user | `current_review`, `last_graded` (one-level undo snapshot), `last_reviewed_at`, legacy `has_pending` | `ReviewStateStore` |

Decisions: one-level undo only (deeper undo corrupts grading); undo restores the
snapshot only if `review_rev` still matches. Reviews generate fresh content; the stored
card is a fallback when every provider call fails (not counted against quota).
A separate `review_attempts` collection was tried and dropped: nothing needed history,
and it split the scheduler's "due" query across two collections.

### Ownership fixes

- [x] **One creator of user documents.** `UserService.record_seen` (trace middleware,
  now awaited before the handler) is the only upsert on `users`; every other writer
  updates existing users only. Before, a user's first update could reach a handler
  that upserted without `created_at` (save, settings, pause), and `$setOnInsert` never
  filled it later: such users keep the trial (plus) limits forever.
  Existing users missing `created_at`: `flashcard.migrations.backfill_created_at`
  (rollout step 3). Dead `ExpressionService.update_user_last_push` removed.
  Guarded by `tests/unit/test_user_creation_contract.py`: only `record_seen` may
  upsert `users`, and the Telegram dispatcher must run `TraceMiddleware`.
  **Mini App:** its auth/launch step must call `record_seen` too; add its test there.
- [x] **`ExpressionService` no longer writes `users`.** Review state moved to
  `ReviewStateStore`: `mark_pending` (send), `clear_pending` (save, import, remove),
  `record_reviewed` (grade: `last_reviewed_at` + clear `has_pending`, one update).
  `last_push_at` is no longer written (never read). Guarded by
  `tests/unit/test_data_ownership.py`: only `UserService`, `ConsumptionService` and
  `ReviewStateStore` write `users`. `TRIAL_DAYS` replaces the literal 14.
- [x] **Typed settings setters.** `UserService.update_setting(field, value)` wrote any
  field. Replaced by `set_target_level`, `set_review_interval`, `set_primary_language`,
  `set_secondary_language`, `set_review_mode`; each enforces its rules (now in
  `schemas/user.py`, next to the fields). `SettingsUseCases` only parses input.
- [x] **Idempotent toggles.** Pause/Resume and the review-mode button were read-then-write
  flips: a double tap or a stale button flipped the setting back. The buttons already
  name what the user wants, so they now call `set_active(active)` and
  `set_review_mode(mode)` (single `$set`, atomic). The review-mode button's callback
  names the other mode. `toggle_active_status` and the unused `get_user_status` removed.
- [ ] `ExpressionService.get_review_candidate` still reads `users.review_mode`;
  the use case should pass it in.

- [x] **Per-user isolation in the scheduler.** One unreadable user document (schema
  error, bad date) no longer stops a tick: `find_users_due_for_review` skips it, logs
  it and reports it to the admin with the send failures (`Unreadable user document`).
  The shadow compare counts such users as `unreadable`. A bad document is reported
  every tick until fixed.

## Deferred issues (do not forget)

- **Quota as its own concept (#6).** Callers ask two separate questions:
  `can_generate_card()` then `card_limit()` for the message. Replace with one
  call, e.g. `quota.check_card(user) -> Allowed | Exceeded(limit)`, that owns
  tier limits, the trial and own-key handling.
- **`/get` vs scheduler differences**, pinned by tests and kept for now:
  `user_id` is `int` in `/get` and `str` in the scheduler (#9); `/get` reloads the
  user, the scheduler reuses it; over quota, `/get` tells the user while the
  scheduler skips silently. Decide deliberately, then unify.
- **Redundant grade check in `ExpressionService.grade_expression` (#3).** It
  still checks `0 <= grade <= 5` and returns `None`, which callers cannot tell
  apart from "card not found". `ReviewUseCases.grade` now validates grade and
  direction first, so remove the service check (and the `None` overload) when
  services are cleaned up.
- **Creation flow quirks**, pinned by `test_creation_flow.py` and kept for now:
  - Unclear input (`card.success == False`) calls the LLM but is not counted
    as usage, so failed generations are free and invisible to quota (#6).
  - Creation passes user preferences to the LLM without the defaults review
    uses (`DEFAULT_LANG_LEVEL`, `DEFAULT_LANG_1_CODE`); with no secondary
    language, creation sends label `None` while review sends 🌍. Unify.
  - Regenerate failure (quota, unclear input) replaces the card and removes
    the Save/Regenerate buttons, so the user can neither retry nor save.
- **Usage counting differs between flows (#6).** `/import` counts every
  answered LLM call (one card generation per import); creation counts only
  successful cards. Pick one rule when quota becomes its own concept.
- **"Own API key" is never used for LLM calls (#6).** Pending feature; gets
  its own module after the refactor is finished. `user.api_config` only
  switches quota to `uses_own_key=True` (unlimited, counted under `user_api`);
  `LLMService` always calls with the system keys. Users with `api_config` get
  unlimited system-key usage. The quota message advertises own keys in
  /settings, but that section only says "reach out to admin (Feature pending)".
- **Unused locale keys.** 4 keys exist in both locales but no code uses them:
  `callbacks.save.success_alert`, `callbacks.regen.failed`,
  `commands.get.generation_error`, `messages.buttons.verb_web_table`.
  Remove or wire up (e.g. regenerate failure, verb web link).
- **i18n returns the raw key when the UI locale lacks it.** There is no
  fallback to English. `test_locales.py` now keeps locales in sync, but a
  real fallback would be safer (#7, with the i18n singleton).
- **Onboarding is spread across use cases.** `claim_first_review_tip` and
  `claim_first_save_tip` are the same pattern on different steps. Move them
  into one onboarding concept when a third tip appears or with #3.
- **Settings leftovers:**
  - Legacy settings menus (callback value `"toggle"`) still use the read-then-write
    `SettingsUseCases.toggle_review_mode`; remove it once old menus no longer matter.
  - Pause/resume/close buttons match text from the deployment locale only (#1, #7).
  - "none" is stored as the string `"none"`, not `None`; readers check both.
- **Story/verb leftovers:**
  - Verb lookups are counted but not limited, by design: they use our own
    scraper and DB cache, no paid provider.
  - `VerbService.is_valid_verb` still strips `/verb` itself (harmless; clean up with #3).
- **Trace middleware writes users.** It awaits `user_service.record_seen` on every
  message/callback (creates the user, `last_seen_at`, `username`) (#3).
  Inline queries are not counted as "seen".
- **Expression queries disagree (#3, #8).** `get_all_expressions` ignores
  `status`, while search and remove only touch `status: "active"`; its `-t`
  path uses `find` (keeps duplicates), the default uses `distinct`. `/story`
  still calls `get_all_expressions` directly (story step).
- **Dates stored as text hide bad values (#9).** A `last_reviewed_at` that is not an
  ISO date can sort after real dates, so the scheduler's DB prefilter never returns
  that user: they silently never get reviews. Real dates would fix it.
- **Duplicated startup** in `bot.py`: `init_telegram_bot` and
  `init_telegram_without_fastapi` build the same services twice (#10).
